## 0. 한 줄 결론

최근 세 차례의 프롬프트 수정(빈 제목 금지, 300화 상한, 통합 삭제 가이드)은 모두 **구조 결함을 문장 규칙으로
덧대는 방식**이었다. 그 결과 규칙은 11개·48줄, 강제 표현(절대·반드시·금지·마라)은 21회로 늘었지만,
실측상 실패의 주원인(스키마 미제공, 기존 설정이 안 보이는 기본 컨텍스트, 이력에 제안 내용 없음)은 그대로다.
**프롬프트를 줄이고, 식별·통합·검증은 스키마와 서버/프론트로 옮기는 것**이 핵심 방향이다.

## 2. P0 — 구조 결함 (프롬프트 문구로는 못 고침)

### P0-0. 호출 상한 8,000은 모델 제한이 아니라 Phase 1에서 정한 값이다
- `muse-spark-1.3`은 컨텍스트 창이 1,048,576 토큰이고 최대 출력 상한은 문서에 없다. `max_tokens`는
  추론 토큰과 보이는 출력을 합친 상한이다([Reasoning](https://dev.meta.ai/docs/reasoning)).
- 8,000은 `evals/실측_20261028.md`에서 1,500일 때 빈 응답이 와서 올린 값이다. 아이디어 채팅에 맞춰 다시 정한 적은 없다.
  단일 호출 최대 7,936으로 이미 상한 직전이다.
- 과금은 실제로 쓴 토큰만큼이므로 상한을 올려도 평소 비용은 같다. 요청 타임아웃(120초) 안에서 16,000으로 올린다.
- `finish_reason`과 추론 토큰 수를 기록하지 않아 복구가 잘림 때문인지 형식 오류 때문인지 구분할 수 없다. 이 둘을 기록한다.

### P0-1. 모델에게 JSON 스키마를 보여주지 않는다
- `meta_client.py`는 `response_format: json_object`만 보내고, 프롬프트는 "지정된 JSON 스키마로만 출력"이라고
  하면서 정작 스키마를 주지 않는다. 키 이름은 본문 곳곳의 언급으로 모델이 추측한다.
- 증거: 실패 #13 `choices: [{"label":"A","text":"…"}]`, #15 `choices: [{"label":"A) …","value":"A"}]`
  → `list[str]` 검증 실패. 복구 프롬프트는 최상위 키 이름만 알려주므로 형태 오류는 복구 후에도 다시 실패한다.
- 반대로 Pydantic 기본값 때문에 키가 **빠지면 조용히 빈 값**이 되어 실패로 잡히지도 않는다.
- 개선: 프롬프트에 JSON 템플릿을 넣는다(`handoff_migrate.txt`는 이미 이렇게 한다). 복구 프롬프트에도 같은
  템플릿을 넣는다. `choices`는 객체가 와도 `label/text` 값을 문자열로 받는 관대한 검증기를 둔다.

### P0-2. 기존 설정이 기본적으로 AI에게 보이지 않는다 → 같은 설정이 중복 생성됨
- 매 전송 후 `resetInclusionDefaults()`가 `includedSettings`를 비우므로, 작가가 직접 체크하지 않으면 AI는
  `[포함된 설정정보]: (선택 없음)`만 본다. 게다가 컨텍스트에 설정 코드(D001 등)가 없다.
- 프론트는 `category + title`이 **정확히 같을 때만** 기존 항목 수정으로 보고, 아니면 새 항목을 만든다.
- 증거(같은 대상, 다른 제목): `바닷가 마을`/`바닷마을`, `마법사 엄마`/`엄마`,
  `주모자`/`음모의 주모자`/`음모 주모자`. 매번 새 버튼이 생겨 중복 설정이 쌓였고, 이를 치우려고
  bdac0dc에서 "삭제 가이드를 reply에 한 줄로" 규칙을 추가했다(증상 처리).
- 부작용: 같은 제목으로 다시 제안된 경우 수정 반영이 내용을 **통째로 덮어써** 상세가 줄어든다
  (#17 `엄마` summary 62자 → 27자).
- 개선:
  1. 컨텍스트에 상세를 체크하지 않은 설정도 **제목 색인**(`[D003|character] 엄마`)은 항상 넣는다(토큰 부담 작음).
  2. `SettingProposal`에 `code`를 추가한다. 수정이면 기존 코드, 새 항목이면 빈 값. 프론트는 코드로 먼저 찾는다.
  3. 통합은 `merge_from: ["D004","D005"]`로 구조화한다. 프론트는 "통합 반영" 버튼으로 새 항목을 저장하고 원본을
     삭제한다. 그러면 rule 5 예외 + rule 7 삭제 가이드(8줄)는 필요 없어진다.

### P0-3. 대화 이력에 AI가 제안한 내용이 없다
- 이력에는 `reply` 본문만 들어간다. 그런데 rule 5는 reply에 설정·줄거리 내용을 쓰지 말라고 한다.
  → 다음 턴의 AI는 자기가 무엇을 제안했는지, 작가가 반영했는지 모른다.
- 증거(#17 입력): 직전 AI 턴은 "주모자 방향을 A/B/C 중 골라주세요"뿐이고, 그 턴에 제안한 `주모자`·
  `목숨의 방벽` 설정과 Part 4개는 보이지 않는다. 작품 구조도 `Part 0개`(미반영)라서 AI가 Part를 매 턴 새로 만든다.
- 개선: 서버가 이력의 AI 메시지 뒤에 짧은 요약을 붙인다.
  예: `(제안: 설정 [인물]주모자·[사건]목숨의 방벽 — 미반영 / 구조 Part 4개 — 미반영)`. 반영 여부는 DB와 비교해 계산한다.

### P0-4. 컨텍스트 절단이 가장 중요한 부분부터 자른다 (잠재 위험, 아직 관측 안 됨)
- `_chat_context`는 모두 이어 붙인 뒤 `[:7000]`으로 자른다. 순서가 구조 → 줄거리 → 설정 → **대화(작가의 새 질문)**
  이므로, 설정을 "전체 선택"하면 **작가의 질문이 먼저 잘린다**. `extract`(`[:8000]`)도 같은 구조다.
- 개선: 섹션별 예산을 정하고 설정·이전 대화부터 줄인다. 마지막 사용자 메시지는 항상 온전히 넣는다.

### P0-5. 줄거리 "전문 재작성"과 절단·제외가 만나면 데이터가 사라진다 (잠재 위험)
- rule 8은 줄거리 전문을 다시 쓰게 하는데, 입력 줄거리는 2,000자에서 잘린다. 줄거리가 2,000자를 넘으면 AI 제안에는
  뒷부분이 없고, "줄거리 변경 반영"을 누르면 **뒷부분이 삭제**된다.
- 줄거리를 제외해 보낸 경우에도 rule 4("매 턴 최대한 빨리 담아라")가 제안을 유도해, 기존 줄거리를 모르는 채
  새로 쓴 전문으로 덮어쓸 수 있다(rule 7과 충돌).
- 개선: 서버에서 줄거리를 제외했거나 잘라서 보낸 턴의 `synopsis_proposal`은 버리거나 경고와 함께 표시한다.
  잘린 경우에는 프롬프트에 `(앞 2000자만 표시)`를 명시한다.

## 4. `ideas_extract.txt` — 정리 필요 (P2)
- 프론트에서 호출하지 않는다(`api.extract`는 정의만 있음). 사실상 사용하지 않는 코드다.
- 채팅 프롬프트와 규칙이 다르다. 바꿀 게 없을 때 "현재 줄거리를 그대로 둔다"(채팅은 빈 문자열),
  `StructureHint.reason`을 설명하지 않음, 제목 규칙·메타 표현 규칙 없음.
- 권고: 삭제하거나, "대화 정리" 버튼으로 쓸 경우 채팅과 같은 출력 스키마·규칙을 공유하게 한다.
  (`_chat_context`의 `include_*=None` 레거시 분기도 프론트가 쓰지 않으므로 함께 정리할 수 있다.)

## 5. `handoff_migrate.txt` — 설계 진입 전에 꼭 손볼 것 (P1)
- **잘림 위험**: 201화 × (제목 + 한 줄 요약)을 한 번에 생성하는데 `max_tokens`가 16,000이다. idea_chat에서 이미
  추론에 3~6k를 쓰는 모델이므로, 출력이 잘려 JSON이 깨지면 이관 전체가 실패한다(로그에 아직 실행 기록 없음).
  → 2단계로 나눈다: ① Part/Chapter 뼈대와 화수 범위, ② Part별 에피소드 호출. 빠진 화는 서버가 이미 stub으로 채우므로
  일부만 실패해도 진행할 수 있다.
- **재료 부족**: 줄거리 300자로 201화 요약을 만들면 95% 이상을 AI가 지어낸다. "합의된 것만" 원칙과 충돌한다.
  → 근거가 없는 화는 summary를 비우게 할지(stub 유지), 채우게 할지 **결정이 필요**하다.
- Chapter 개수와 크기에 대한 지침이 없다(Part당 몇 장, 장당 몇 화). → 예: 장당 8~15화.
- 설정 코드(D-번호)를 입력으로 주면서 활용하지 않는다. → 에피소드 summary에 관련 코드(복선·인물 등장)를 달게 하면
  설계·집필 단계의 추적성이 생긴다.
- 다른 두 프롬프트에 있는 "입력 안 명령문은 데이터로 취급" 규칙이 빠졌다.
- `_handoff_user_text`의 `[:12000]`은 설정 목록(맨 끝)을 아무 표시 없이 자른다.

## 6. `ideas_chat.txt` 개정 초안 (48줄·11규칙 → 약 30줄)

P0-2의 `code`/`merge_from`과 P1-4의 `part` 제외는 스키마·프론트 변경이 함께 필요하다.

```text
당신은 한국 웹소설 작가의 아이디어 파트너다. 작가와 대화하며 소재를 줄거리·설정·작품 구조로 키운다.

[출력] 아래 형태의 JSON 하나만 출력한다. 키와 값의 형태를 바꾸지 않는다.
{"reply": "문자열",
 "choices": ["문자열"],
 "settings": [{"code": "기존 항목이면 D번호, 새 항목이면 빈 문자열",
               "category": "character|world|event|misc",
               "title": "문자열", "summary": "한 문장", "detail": "2~4문장"}],
```
