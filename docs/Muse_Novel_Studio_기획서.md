# Muse Novel Studio

Meta AI 기반 장편 웹소설 자동 창작 플랫폼 종합 기획서

2026년 10월 28일 | Meta Global AI Developer Hackathon | 개인 개발자 트랙

목적: 작가와 AI가 장편 작품의 전체 방향을 공동 설계한 뒤, Meta 모델 기반 에이전트가 집필·검증·교정·기억 관리를 자율 수행하고 작가가 10화 단위로 승인하는 제품을 정의한다. 본 문서는 대화에서 확정한 결정, 설계 제안, 해커톤 범위를 구분한다.

## 1. 프로젝트 비전과 확정 원칙

- 작가는 처음에 키워드와 방향을 제공하고 AI와 충분히 대화하여 작품 콘셉트를 확정한다.
- 본격 집필 전 전체 목표 분량(예: 200화)의 구간별 구성과 회차별 짧은 개요를 작성해 작가 승인을 받는다.
- AI는 승인된 설계도에 따라 기획·집필·설정 검증·서사 검토·문장 교정·품질 평가를 수행한다.
- AI는 10화씩 제작하고 작가의 승인 후 다음 10화를 제작한다. 수정 요청이 있으면 재검증한다.
- 승인 전 설정 및 원고 변경은 임시 상태로 보관한다. 승인 후만 공식 기억으로 확정한다.
- 중대한 세계관·결말 변경은 AI가 독단적으로 확정하지 않고 작가에게 제안한다.

## 2. 사용자의 전체 여정

### 화면을 다음과 같이 구현을 하자

- 메인 -> Dialog로 작품 명을 입력 받고 다음 화면으로 넘어 감
  각 작품별로 고유 UID를 가지고 있어서 바로 해당 작품의 화면으로 외부에서 고유 URL즉 LINK로 연결할 수 있도록 구현함
- 아이디어 / 구조  (신규: 기존의 1.작품.설계를 세분화하여 앞부분으로 구현) : 작품의 길이와 구성을 결정하는 수준. 작품은 기본적으로 Part -> Chapter -> Episode -> Scene 구조가 기본이고 이 뼈대를 확정 짖는 단계. 예, 약 25 Episode의 중편이면 Chapter -> Episode -> Scene 으로 충분하다. 장편으로 약 200 Episode의 글이면 Part -> Chapter -> Episode -> Scene 구조가 필요하다.
- 세부 설계 (신규: 기존의 1.작품.설계를 세분화하여 뒷부분으로 구현) : 정의한 Part -> Chapter -> Episode -> Scene 구조를 기준으로 top-down으로 story를 만들고 필요한 설정들을 정의한다.
- 집필 : Espisode단위로 글을 작성한다. 
- 작가검토: 집필한 것의 일관성, 설정오류 점검, 흥미로운 진행인지, 등 소설의 품질을 분석하여 최종 점검을 한다
- 출판: 출판 대기 작품 목록과 실제 출판 요청 및 출판 완료 상태관리를 한다. 출판은 외부 전문 출판 업체에 전달을 한다. 지금은 문피아에게 전달하는 것으로 한다. 이것을 위하여 1.표지그림, 2.설명글을 별도로 준비하도록 한다. 그리고 출판에서 등록한 사용자의 feedback을 등록하여 향후 글에 참고를 할 수 있도록 한다

#### **'메인' 화면 설계 **

**목적:** 새 소설을 시작하거나 기존 작품의 작업을 이어 간다.  
**경로:** `/`

| 영역 | 표시 내용 및 동작 |
|---|---|
| 상단 | Site 로고, 전체 작품의 AI 사용 기록을 여는 ‘AI로그’ 버튼 |
| 시작 안내 | 소개 문구, ‘새로운 소설 만들기’ 버튼 |
| 목록 도구 | 전체 작품 수, 제목 검색, 최근 수정 순 정렬 |
| 작품 카드 | 제목, 작업 단계, 완성 Episode 수, 최종 수정일, ‘이어 쓰기’, ‘삭제’ |
| 하단 | 서비스명과 짧은 안내 문구 |

**주요 동작**

- **새로운 소설 만들기:** 제목 입력 창 → 제목 입력(필수, 최대 80자) → 생성 → 아이디어 발굴 화면으로 이동.
- **이어 쓰기:** 카드 선택 → 해당 작품의 마지막 작업 단계로 이동. 단계는 아이디어 / 구조-> 세부 설계 -> 집필 중에서 최종단계의 화면을 선택하자.
- **검색:** 입력한 제목을 포함하는 작품을 즉시 표시.
- **삭제:** 확인 창에서 작품 제목을 동일하게 입력 → 영구 삭제. AI 사용 기록은 유지.

**상태 및 화면 대응**

- 작품 없음: 첫 소설 만들기 안내.
- 검색 결과 없음: 안내와 ‘전체 소설 보기’ 제공.
- 불러오는 중·실패: 상태 표시와 재시도 제공.
- 생성·삭제 처리 중: 중복 실행 방지.
- 반응형: 작품 카드 PC 3열 → 태블릿 2열 → 모바일 1열. 모바일에서는 책 이미지 생략.

**시각 방향:** 아이보리 배경, 짙은 녹색 강조, 책장을 연상시키는 카드와 여백 중심 구성.

#### **'아이디어 / 구조'  화면 설계 **

**목적:** AI와 대화하며 소재를 발전시키고, 작품 방향과 작품의 길이와 구성을 결정하고 관련 설정을 정리해 세부 설계로 넘긴다.  
**경로:** `/novels/{작품 ID}/ideas`

| 영역 | 표시 내용 및 동작 |
|---|---|
| 상단 | 작품 선택·이름 변경, 메인화면 이동, 작업 단계, 연결 상태, AI로그 |
| 왼쪽: 아이디어 대화 | AI와 채팅하는 곳. AI와 소재·줄거리·설정을 논의하고 발전시킴. 선택지 응답, 새 대화 생성·기존 대화 전환, 메시지 입력.  |
| 오른쪽 상단: '전체 줄거리' | 작품 전체의 이야기 흐름을 별도 문서로 관리. 직접 수정하거나 AI의 수정 제안을 적용 |
| 오른쪽 하단: '설정정보' | 인물·세계관·사건·최상위 Part의 이야기 등 작가가와 이야기 하면서 소설설계에 필요하다고 생각되는 사항들을 항목별로 관리 |
| 설계 전환 | ‘아이디어 마무리 → 소설설계로’ 버튼 |

**주요 동작**

- **아이디어 발전:** 자유롭게 입력하거나 AI가 제시한 선택지로 대화를 이어 간다. 최종 목표는 작품의 길이와 구성을 결정하는 수준. 작품은 기본적으로 부(Part) -> 장(Chapter) -> 화(Episode) -> 장면(Scene) 구조가 기본이고 이 뼈대를 확정 짖는 단계. 예, 약 25 Episode의 중편이면 Chapter -> Episode -> Scene 으로 충분하다. 장편으로 약 200 Episode의 글이면 Part -> Chapter -> Episode -> Scene 구조가 필요하다. 이 단계가 종료하기 전에 아 구조가 확정이 되도록 채팅에서 AI가 사용자를 이끌어야 한다.
- **설정 정리:** AI가 제안한 내용은 사용자가 적용해야 설정으로 저장된다.
- **자료 참조:** `@` 또는 ‘대화에 참조’로 필요한 설정을 첨부하고, AI에 보낼 대화 범위를 선택한다.
- **자료 관리:** 변경 자동 저장, 승인된 작품 방향·설정의 Markdown 다운로드.
- **설계 인계:** 미처리 제안과 재검토 항목을 정리한 뒤 전달 내용을 확인한다. 인계 후 아이디어는 읽기 전용으로 전환된다.

**'설정정보' 표시 방식**

| 모드 | 표시 규칙 |
|---|---|
| **한줄** | 설정마다 한 줄로 표시하고, 넘치는 내용은 `…`로 생략 |
| **이어서** | 내용을 생략하지 않고 줄바꿈하여 이어 표시 |
| **전체** | 모든 설정의 상세 내용과 편집·참조 버튼을 펼쳐 표시 |

한줄·이어서 모드에서는 항목을 누르면 해당 설정의 상세 내용을 펼칩니다. 선택한 표시 방식은 유지합니다.

**'전체 줄거리' 관리**

- 설정에 관한 대화를 이어 가면서 전체 줄거리도 계속 수정·보완합니다.
- AI는 논의한 설정이 줄거리에 미치는 영향을 검토하고, 필요한 줄거리 변경을 함께 제안합니다.
- 변경 전후를 확인하고 사용자가 적용하면 줄거리를 갱신합니다.
- 전체 줄거리와 개별 설정은 구분해 저장하고, 소설설계로 함께 인계합니다.

#### **소설설계 화면 설계서 — 이야기의 구조와 흐름**

**목적:** 아이디어 / 구조에서 넘긴 전체 줄거리와 설정을 바탕으로, Part·장·화의 이야기를 구체화하고 집필할 화를 준비한다.  
**경로:** `/novels/{작품 ID}/design`

| 영역 | 표시 내용 및 동작 |
|---|---|
| 상단 | 작품명, 작업 단계 이동, 저장 상태, Markdown 다운로드, AI로그 |
| 왼쪽: 소설 구조 | 작품 → Part → 장 → 화 → 장면의 계층 목록. 추가·이동·보관·검색 |
| 중앙: 설계 편집 | 선택한 항목의 줄거리·상세 설계·관련 설정을 확인하고 수정. 상단에 줄거리를 보여 주고 만일 바로 아래 하위의 줄거리가 있으면 각 노드의 한줄 줄거리도 같이 보여 주도록 하자. |ㅜ
| 오른쪽: 설계 파트너 | 선택한 항목에 대해 AI와 대화하고 변경 제안 검토. 설계 파트너는 선택된 노드의 하위 노드들의 줄거리까지 설계를 할 수 있다. 선택된 노드가 '작품'이면 전체 이야기에 대한 설정정보이고 그 하위 노드에 대한 줄거리까지 정의할 수 있게 하자. 만일 아이디어에서 Part와 Chapter없이 Episode로만 구성하겠다고 정의를 하면 작품의 바로 밑의 노드는 Episode가 된다.  |


**설계 내용**

- **작품:** 전체 줄거리, 작품 방향, 공통 집필 기준. 
- **부(Part)·장(Chapter):** 해당 구간의 이야기, 주요 사건, 시작과 끝의 변화.
- **화(Episode):** 화의 스토리, 핵심 변화, 선행 조건, 숨은 플롯, 후속 결과.
- **장면(Scene):** 필요할 때 추가하는 세부 전개와 메모.
- 각 설정은 고유 ID를 부여 한다. 작품은 'N',Part는 'P', Chapter는 'C', Episode는 'E', Scene은 'S'를 시작하는 3자리 숫자로 부여하자. 이것을 이용하여 '@'을 이용한 참조에서 사용하자.

**주요 동작**

- **자료 인계:** 아이디어의 전체 줄거리·설정·Part 이야기를 이어받아 설계의 출발점으로 사용한다.
- **단계별 구체화:** 전체 → Part(Optional) → 장(Optional) → 화로 이야기를 발전시킨다.  Part,장은 아이디어 단계에서 사용하지 않기로 결정할 수 있다.  하위 내용이 바뀌면 상위 줄거리의 보완 필요 여부도 검토한다.
- **AI 협업:** `@`로 설정이나 다른 구조 항목을 참조한다. AI의 변경안은 사용자가 적용해야 반영된다.
- **표시 방식:** 구조 목록과 설정정보는 **한줄·이어서·전체** 모드를 지원하고 선택을 유지한다.
- **집필 연결:** 준비된 화의 집필 지시서를 확인하고 글쓰기 화면으로 이동한다. 전체 설계를 끝내기 전에도 화별 집필을 시작할 수 있다.

- 현재의 '설계도 생성'은 Chapter를 선택하고 Episode를 설계하는 작업으로 매칭이 되어야 할 것 같다.


**화면 대응:** PC는 너비 조절이 가능한 3개 영역, 모바일은 ‘구조 / 설계 / 설계 파트너’ 탭으로 표시한다. 변경은 자동 저장한다.


## 3. 200화 계층형 서사 계획

200화를 한 번에 상세 집필하지 않는다. 먼저 전체 서사의 시작·전환점·결말을 정한 뒤 큰 구간과 10화 묶음, 개별 회차의 요약으로 구체화한다. 예시 구간은 1–40화 도입, 41–80화 성장, 81–120화 위기, 121–160화 대결 준비, 161–200화 결말이다. 실제 분할은 작품 특성에 맞춘다.

- 각 회차 계획 필드: 번호, 가제, 핵심 목표, 주요 사건, 인물 변화, 복선 설치·회수, 직전·다음 회차 연결, 필수/선택 제약.
- 전역 검증: 갈등의 장기 지속성, 사건 중복, 복선 회수, 인물 동기, 결말 인과관계, 전개 속도.
- 승인된 설계도는 버전 관리한다. 실집필이 달라질 경우 영향받는 후속 회차 계획을 추적한다.

## 4. 에이전트 구성과 Meta 활용

| 역할 | 주요 책임 | 권장 Meta 활용 |
|---|---|---|
| AI 편집장 | 작업 오케스트레이션, 품질 게이트, 재시도, 승인 요청 | Muse Spark 추론·도구 호출 |
| 스토리 아키텍트 | 콘셉트 협의, 200화 설계, 회차 목표 설정 | Muse Spark |
| AI 작가 | 설정 및 장면 계획에 따라 원고 생성 | Muse Spark |
| 일관성 검증자 | 인물·규칙·시간·복선 충돌의 출처 기반 탐지 | Muse Spark + DB·검색 도구 |
| 서사 편집자 | 개연성·페이싱·대사·감정선 평가 | Muse Spark |
| 교정자 | 맞춤법·문법·문체·반복 표현 수정 제안 | Muse Spark |
| 기억 관리자 | 임시 기억 추출·연결, 승인 후 정식 반영 | Muse Spark 구조화 출력 + DB |

모델 수를 늘리는 것이 목표는 아니다. 동일한 Muse Spark를 역할별 프롬프트와 도구 계약으로 호출해도 충분하다. Muse Image(삽화)·Muse Voice Transcribe(구술 입력)는 추후 확장. Muse Spark Open(파트너 추론)은 특별상 도전 옵션. Muse Code는 개발 보조 수단이다.

## 5. 회차 자동 제작 상태 머신

PLAN → DRAFT → VERIFY → EDIT → PROOFREAD → QUALITY_GATE → READY_FOR_REVIEW → AUTHOR_APPROVED → COMMIT. 품질 검사 실패 시 구체적 수정 작업을 만들어 DRAFT/EDIT로 되돌리고 재검증한다. 재시도 횟수와 비용·시간 한도를 넘으면 작가에게 미해결 이슈를 제출한다.

- 10화 내부에서는 앞 회차의 임시 설정을 뒤 회차에 참조할 수 있다.
- 작가가 7화 내용을 고치면 영향받는 8~10화를 재검증하고 필요 시 다시 생성한다.
- 작가 승인 전에는 공식 세계관 DB와 확정 원고를 덮어쓰지 않는다.
- 각 호출의 입력, 모델 버전, 출력, 사용 토큰, 판단 근거, 수정 이력을 기록한다.

## 6. 기억과 일관성 검증 설계

| 객체 | 주요 필드 |
|---|---|
| Character | 식별자, 성격, 능력, 상태, 관계, 적용 시점, 출처 |
| Event | 사건, 참가자, 발생 시점, 결과, 선행 조건, 원문 출처 |
| WorldRule | 규칙, 예외, 도입·폐기 시점, 근거 회차 |
| Foreshadowing | 복선, 설치 회차, 예상 회수 시점, 상태, 근거 |
| Chapter | 계획 버전, 원고 버전, 승인 상태, 이슈, 검사 결과 |
| StylePolicy | 시점, 문체, 분량, 작가가 승인한 피드백 |

검증은 구조화된 기억 검색과 원문 조회를 결합한다. AI가 제시한 인용문은 저장된 실제 원문과 기계적으로 대조한다. 설정은 단순 참/거짓이 아니라 유효 시점을 가진다. 예를 들어 8화의 능력 부족과 27화의 각성은 모순이 아닐 수 있다. 불확실한 항목은 오류로 확정하지 않고 검토 필요로 표시한다.

## 7. 작가 검토 화면 요구사항

- 10/200화 진행률과 현재 10화 묶음의 상태 표시.
- 각 회차 원고, 회차별 요약, 오류 탐지 및 자동 수정 내역, 남은 이슈 목록 제공.
- 전체 기획 대비 진행 차이 및 다음 묶음 예고 표시.
- 개별 회차 수정 요청, 변경 전후 비교, 10화 묶음 최종 승인 기능.
- 작가의 문체 피드백은 승인된 스타일 정책으로 저장하며 모델 파인튜닝으로 오해하지 않도록 명시.

## 8. 권장 시스템 구성

| 영역 | 권장안 |
|---|---|
| 웹 UI | Next.js / React |
| API | FastAPI |
| 모델 | Meta Model API Muse Spark |
| 워크플로 | 재개 가능한 DB 기반 상태 머신 |
| 데이터 | PostgreSQL JSONB + 전문 검색, 필요 시 pgvector |
| 비동기 작업 | 작업 큐 또는 안전한 백그라운드 워커 |
| 관측성 | 각 에이전트 결과·토큰·비용·지연·검증 로그 |

모든 AI 결과는 JSON 스키마로 검증하고, 생성된 원고와 제안된 수정은 버전별 저장한다. API 오류·중단 시 재개 가능하게 설계한다. 장기적으로 동시 사용자, 저작권, 접근 통제, 비용 상한 정책을 추가한다.
