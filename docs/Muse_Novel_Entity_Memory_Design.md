# Muse Novel Studio — 회차별 엔티티 기억·이력 관리 설계

작성일: 2026-10-28  
상태: 논의 내용 정리 및 구현 제안 초안

## 1. 목적과 핵심 원칙

200화 규모 장편 집필에서 과거 모든 원고나 요약을 매번 AI에 전달하지 않고도 인물·장소·사건·물건·조직·관계의 연속성을 유지한다. 이를 위해 관리 대상을 **엔티티(Entity)**로 통일하고, **N화 집필은 승인된 N-1화 종료 상태를 기본 맥락으로 사용**한다.

- 과거 정보는 삭제하지 않고 회차별 조회 가능하게 보관한다.
- 다음 화에 전달할 것은 과거 상태들의 나열이 아니라 직전 화까지 누적된 **유효한 최신 상태**다.
- 미래 회차의 사건이나 역할을 현재 사실로 추정·기록하지 않는다.
- 회상, 과거 거주지, 오래된 사건 등 특별한 경우에만 과거 이력을 조회한다.
- **원고 집필 중 엔티티 추출·저장 작업을 수행하지 않는다.** 한 화의 원고가 완성된 뒤 후처리한다. 단, 집필 중 필요한 기존 정보의 *조회*는 허용한다.
- AI는 자연어 해석·추출·변경 제안을 맡고, 프로그램은 조회·식별자 관리·검증·버전 기록·저장을 수행한다.
- 작가 승인 전 변경은 임시 상태로 두며, 승인된 원고에 대한 변경만 공식 기억에 반영한다.

## 2. 엔티티 모델

엔티티 유형 예시: `character`, `location`, `event`, `item`, `organization`, `relationship`. 유형별 속성은 확장 가능하게 설계한다.

엔티티는 다음 세 층으로 관리한다.

1. **식별·기본 정보:** 고유 ID, 유형, 정식 명칭, 별명·동의어, 최초 등장 회차.
2. **현재 상태:** 특정 회차 종료 시점에 유효한 속성들(나이, 거주지, 소지품, 관계, 부상 등).
3. **변경 이력:** 어떤 속성이 어떤 값에서 어떤 값으로, 어느 회차에서, 어떤 근거 문장에 따라 바뀌었는지.

**회차 번호와 이야기 속 시간은 별개**다. `recorded_episode`(원고에서 기술된 회차)와 `story_time`(이야기 세계에서 사건이 실제 발생한 시점, 불명확할 수 있음)을 구분한다. 회상 장면에서 기록된 과거 사건이 현재 상태를 잘못 덮어쓰지 않도록 한다.

## 3. 회차별 상태 예시

| 회차 종료 | 나이 | 거주지 | 성격 | 이번 회차에서의 변화 |
|---|---|---|---|---|
| 1화 | 10살 | 서울 | 소심함 | 최초 등록 |
| 2화 | 12살 | 서울 | 소심함 | 나이 변경 |
| 3화 | 12살 | 제주 | 소심함 | 제주로 이사 |
| 4화 | 12살 | 부산 | 소심함 | 부산으로 이사 |

5화 집필 기본 정보는 **12살, 부산 거주, 소심함**이다. 1화의 나이·3화의 거주지를 매번 함께 보내지 않는다. 다만 ‘부산 전에 어디 살았는가?’라는 질문이 있으면 이력을 조회해 3화의 제주 거주를 반환한다. 이사 회차와 실제 이사 시점이 다를 수 있으므로 그 차이는 별도 필드로 관리한다.

## 4. 한 화 완성 후 엔티티 반영 파이프라인

1. **원고 완료:** N화의 원고 버전을 고정한다. 아직 공식 기억에는 반영하지 않는다.
2. **엔티티 추출(AI):** 원고 전체에서 인물·장소·사건·물건·관계 등 엔티티 후보와 관련 근거 구간을 추출한다.
3. **엔티티별 요약(AI):** 이번 화에서 실제로 확정된 사실과 변화만 간결하게 요약한다. 언급·추가·변경·명시적 제거를 구분한다.
4. **동일 엔티티 판별(AI 보조 + 프로그램):** 기존 ID·정식명·별명·문맥으로 대조한다. 동명이인·불확실한 동일성은 임의 병합하지 않고 검토 대상으로 남긴다.
5. **상태 비교 및 변경안 생성:** N-1화 종료 상태를 기준으로 새 사실을 추가하고 변경된 속성만 갱신한다. 미언급 속성은 유지한다.
6. **검증:** 근거 누락, 속성 충돌, 시간 역전, 관계 불일치, 기존 사실과의 모순을 점검한다. 회상 속 과거 사실은 현재 상태 갱신과 분리한다.
7. **임시 상태 저장:** N화의 엔티티 변경안과 종료 상태를 초안 버전에 연결한다.
8. **작가 승인:** 원고 승인 시 변경안을 공식 이력에 원자적으로 확정한다. 수정·재생성 시 해당 초안 변경안은 폐기하거나 다시 계산한다.
9. **다음 화 준비:** N+1화에는 승인된 N화 종료 상태를 기준으로 필요한 엔티티만 제공한다.

### 추출 시 주의사항

- **미언급 ≠ 삭제:** 5화에 칼이 나오지 않았다는 이유로 소지품에서 제거하지 않는다.
- **명시적 변화만 반영:** ‘칼을 잃어버렸다’면 소유 상태를 변경한다.
- **추측 금지:** 원고가 밝히지 않은 나이·동기·미래 역할은 생성하지 않는다.
- **불확실성 보존:** ‘죽은 것으로 알려졌다’와 ‘사망이 확정됐다’는 서로 다르다.
- **출처 추적:** 각 변경에는 원고 버전과 근거 구간을 연결한다.

## 5. 집필 전·중·후의 정보 흐름

**집필 전:** N화 줄거리 요약에서 핵심 인물·장소·사건을 식별하고, N-1화 승인 종료 상태에서 관련 엔티티의 최신 정보를 선별한다. 반드시 등장해야 할 인물과 집필 과정에서 자유롭게 추가 가능한 주변 인물을 구분한다.

**집필 중:** 준비된 상태를 기본 맥락으로 사용한다. 예상하지 못한 기존 인물이나 과거 사건이 필요할 때만 조회한다. 새 인물의 창작은 허용하지만, 이때 공식 DB에 즉시 등록하지 않는다.

**집필 후:** 완성된 원고 전체를 다시 분석해 실제 등장·변경된 엔티티를 추출하고 검증·승인 절차를 거쳐 반영한다.

## 6. 엔티티 관리 AI와 프로그램의 책임

| 구성요소 | 책임 | 하지 않는 일 |
|---|---|---|
| 집필 AI | 줄거리와 제공된 상태로 원고 집필, 필요시 과거 조회 요청 | 공식 엔티티 DB 직접 수정 |
| 엔티티 관리 AI | 원고에서 엔티티·변화·근거 추출, 모호한 검색 요청 해석, 변경안 제안 | DB에 무제한 직접 쓰기, 미래 사건 추정 |
| 기억 관리 프로그램 | ID 매칭 후보 검색, 버전·상태 계산, 변경 이력 보관, 회차별 조회, 승인 반영 | 자연어 원고의 의미를 독자적으로 추측 |
| 일관성 검증 기능 | 모순·누락·시간 관계 검증, 검토 항목 생성 | 작가 승인 없이 원고·공식 사실 확정 |
| 작가 | 원고 검토·수정·승인, 불확실한 충돌 최종 판단 | 매회 모든 엔티티를 수동 입력할 필요 없음 |

초기 구현은 **엔티티 관리 AI 1개 + 결정적 저장·조회 프로그램**으로 시작할 수 있다. 검증 기능은 별도 에이전트 또는 동일 모델의 독립 검증 단계로 운영 가능하며, 비용·정확도를 측정해 분리 여부를 결정한다.

## 7. 권장 데이터 구조(개념)

- `entities`: `entity_id`, `type`, `canonical_name`, `aliases`, `first_episode`
- `entity_changes`: `change_id`, `entity_id`, `episode`, `manuscript_version`, `field_path`, `operation`, `old_value`, `new_value`, `story_time`, `evidence`, `status`
- `episode_snapshots`: `episode`, `approval_version`, `state_ref` 또는 계산된 상태 캐시
- `episode_manuscripts`: `episode`, `version`, `approval_status`
- `entity_links`: 엔티티 간 관계와 관계의 유효 시점·근거

변경 연산 예시: `add`, `set`, `remove`, `mention`. `mention`은 정보의 삭제나 변경을 뜻하지 않는다. 실제 저장에서는 `remove`와 '알 수 없음/미확정'을 구분한다.

**구현 선택:** 변경 이력을 원본으로 저장하고, 일정 간격 또는 매 승인 회차마다 스냅샷을 캐시한다. 회차 조회 시 ‘해당 회차까지 승인된 변경’만 재구성한다. 따라서 2화 조회는 2화 종료 상태, 4화 조회는 4화 종료 상태를 반환하며 미래 정보가 섞이지 않는다.

## 8. API 초안

- `get_entity_state(entity_id, as_of_episode)` — 지정 회차 종료 상태 반환
- `get_relevant_entities(episode_outline, as_of_episode)` — 줄거리에 관련된 엔티티 후보와 상태 조회
- `get_entity_history(entity_id, filters)` — 필요한 기간·속성의 이력만 조회
- `propose_episode_changes(episode, manuscript_version, proposals)` — AI 추출 결과를 임시 변경안으로 등록
- `validate_episode_changes(episode, manuscript_version)` — 충돌·근거·시간 관계 검증
- `commit_episode_memory(episode, approved_manuscript_version)` — 승인 버전만 공식 확정

`commit`은 재시도해도 중복 적용되지 않도록 멱등성을 보장하고, 원고 승인 버전과 기억 버전의 일치를 확인해야 한다.

## 9. 주요 예외·위험

1. **동명이인/별명:** 기존 인물과 신규 인물을 잘못 합치지 않도록 ID·문맥 기반 확인.
2. **회상/비선형 서사:** 과거 장면에서 밝혀진 사실을 현재 나이·거주지에 덮어쓰지 않기.
3. **원고 수정:** 승인 전 재작성되면 해당 초안의 추출 결과 재생성. 승인 후 수정은 영향받는 후속 회차의 기억 재계산 필요.
4. **암시·오해·거짓말:** 화자의 주장과 세계의 확정 사실을 구분하고 신뢰도·관점을 기록.
5. **누락된 엔티티:** 원고에서 추출되지 않았더라도 기존 엔티티는 삭제하지 않음.
6. **스냅샷 비용:** 전체 상태를 매번 복사하기보다 변경 로그 + 선택적 캐시를 우선 검토.
7. **미래 계획과 확정 사실:** 200화 전체 줄거리 계획은 별도 보관하며, 아직 발생하지 않은 사건을 현재 엔티티의 사실로 취급하지 않음.

## 10. 최소 구현(MVP) 및 검증

**MVP 범위:** 인물·장소 두 유형부터 시작, 원고 1~5화 처리, 엔티티 추출·속성 변경·회차별 상태 조회·임시 변경·작가 승인·과거 조회를 구현한다.

**필수 테스트**

1. 1화 10살 → 2화 12살: 1화 조회는 10살, 2화 조회는 12살.
2. 3화 제주 → 4화 부산: 5화 집필에는 부산만 기본 전달, 과거 조회는 제주 반환.
3. 5화에 칼이 언급되지 않음: 소지 상태 유지. 명시적으로 잃어버리면 변경.
4. 5화 회상에서 1화의 열 살 시절 언급: 현재 나이가 열 살로 되돌아가지 않음.
5. 5화 초안 변경 후 미승인: 6화 공식 기억에 반영되지 않음. 승인 후에만 반영.
6. 동일 인물의 별명과 동명이인 등장: 동일성 불확실 시 자동 병합 금지.

**완료 기준:** 승인된 회차의 상태 재현 가능, 미래 정보 유입 없음, 근거 없는 삭제 없음, 재승인·재시도 시 중복 기록 없음, 변경별 원고 근거 추적 가능.

## 11. 아직 결정하지 않은 사항

- 엔티티 유형별 필수 속성과 자유 속성(JSON)의 비율
- 엔티티 동일성 판정의 자동 확정 기준 및 사람 검토 기준
- 매회 스냅샷 저장과 주기적 스냅샷의 성능 비교
- 일관성 검증을 별도 AI로 분리할지 여부
- 원고 승인 후 과거 회차 수정 시 후속 상태 재계산·충돌 해결 UX

---

**설계의 한 문장 요약:** 각 화를 완성한 후 AI가 엔티티와 변경 사실을 추출하고, 프로그램이 이를 회차별 이력으로 관리하며, 다음 화는 직전 승인 회차의 최종 상태만 기본적으로 이어받는다.
