# Muse Novel Studio — 엔티티 구조 및 AI 역할 설계서

- 작성일: 2026-10-28
- 문서 성격: 장편 웹소설 제작 앱의 엔티티 기억 관리 및 AI 협업 상세 설계 초안
- 범위: 엔티티 유형, 데이터 구조, 회차별 상태 이력, 추출·검증 프로세스, AI 역할과 구현 우선순위

## 1. 목적과 핵심 원칙

200화 장편소설에서 집필 AI가 매회 모든 과거 원고를 읽지 않도록, 회차 종료 시점의 **유효한 엔티티 상태**를 다음 화에 제공한다. 이전 상태는 삭제하지 않고 이력으로 보존하되, 과거 회상·원인 확인 등 필요할 때만 조회한다.

1. **현재 상태 우선**: N화를 쓸 때 기본적으로 N-1화 종료 시점의 상태를 사용한다.
2. **이력 보존**: 과거 값은 기본 집필 문맥에서 제외하지만 회차별 조회가 가능하다.
3. **미언급은 변경 아님**: 원고에 나오지 않은 속성은 그대로 유지한다.
4. **확정 사실과 미래 계획 분리**: 아직 집필되지 않은 화의 예상 사건을 공식 엔티티 상태에 넣지 않는다.
5. **원고 완성 후 추출**: 엔티티 추출·변경 제안은 한 화의 원고가 완성된 후 수행한다.
6. **AI 판단과 프로그램 저장 분리**: AI는 추출·동일성 판단·변경 제안·검증을 맡고, 프로그램은 조회·버전·트랜잭션·저장을 맡는다.
7. **승인 전 임시 상태**: 10화 묶음 작업 중에는 임시 기억을 사용하고, 작가가 승인한 결과만 공식 상태로 확정한다.
8. **원문 근거 필수**: 변경에는 해당 원고의 문장 위치 및 근거가 연결되어야 한다.

## 2. 엔티티 유형

| 유형 | 예시 | 핵심 속성 | 비고 |
|---|---|---|---|
| Character / 인물 | 주인공, 조연, 악역 | 나이, 성격, 직업, 건강, 능력, 소속, 현재 위치 | 회차별 변화가 빈번 |
| Location / 장소 | 도시, 집, 던전 | 지리적 위치, 환경, 통제 세력, 파괴 여부 | 이동과 별개로 장소 자체 상태 보존 |
| Organization / 조직 | 길드, 기업, 왕국 | 지도자, 목적, 구성원, 영향력, 존속 상태 | 구성원은 관계로 연결 |
| Item / 사물 | 검, 반지, 문서 | 소유자, 위치, 기능, 손상·분실 상태 | 소유권과 위치 검증 |
| Ability / 능력 | 마법, 무공, 스킬 | 효과, 수준, 조건, 제약 | 인물과 보유 관계 연결 |
| Event / 사건 | 사고, 배신, 전투 | 발생 시점, 장소, 참여자, 원인, 결과 | 여러 엔티티 변경의 근거 |
| WorldRule / 세계 규칙 | 마법 법칙, 사회 제도 | 적용 범위, 조건, 예외, 유효 시점 | 원칙적으로 일관성 제약 |
| Knowledge / 정보·비밀 | 암호, 출생의 비밀 | 사실 내용, 보유자, 공개 여부 | 객관적 사실과 인물의 믿음을 구분 |
| Goal / 목표·과제 | 복수, 계약, 탐색 | 주체, 목표, 진행 상태, 완료 조건 | 인물·조직과 연결 |
| Relationship / 관계 | 가족, 친구, 적대 | 양 끝 엔티티, 유형, 강도, 유효 기간 | 독립 객체 또는 관계 레코드로 관리 |

**설계 판단:** 관계는 보통 `entity_relations`로 관리하고, 사건은 독립적인 `events` 기록으로 두는 편이 유리하다. 단, 모든 유형을 처음부터 별도 테이블로 나누지 않는다. 공통 `entities`와 유형별 JSON 속성을 기반으로 시작한다.

## 3. 데이터 구조: 4계층

### 3.1 엔티티 식별자 (Identity)

`entity_id`, `type`, `canonical_name`, `aliases`, `first_episode`, `description`, `lifecycle_status` 등 변하지 않거나 드물게 바뀌는 공통 메타데이터. 이름이 같더라도 동일 인물로 단정하지 않으며, 별칭·동명이인 판정을 별도로 수행한다.

### 3.2 회차별 상태 (State)

`entity_id`, `episode_no`, `attributes`, `status`, `revision_id`. 해당 화 **종료 시점에 유효한 값**을 표현한다. 기본 집필 시에는 직전 회차의 유효 상태를 전달한다. 속성마다 값과 함께 확실성 및 근거를 연결할 수 있다.

### 3.3 변경 이력 (Changes)

`change_id`, `entity_id`, `episode_no`, `attribute_path`, `operation`, `old_value`, `new_value`, `evidence`, `source_revision`, `approval_status`. 변경만 저장하는 이벤트 로그를 기준 데이터로 삼고, 자주 조회하는 회차의 상태는 스냅샷으로 캐시한다.

변경 연산은 `create`, `set`, `add`, `remove`, `end_relation`, `no_change` 등을 구분한다. **원고에서 언급되지 않았다는 이유로 `remove`를 만들지 않는다.**

### 3.4 엔티티 간 관계 (Relations)

`subject_id`, `predicate`, `object_id`, `valid_from_episode`, `valid_to_episode`, `evidence`. 예: `김도윤 --resides_in--> 부산`, `김도윤 --member_of--> 청룡길드`, `김도윤 --owns--> 마법검`. 관계 변경도 이력을 보존한다.

## 4. 회차별 상태 예시

| 회차 종료 | 나이 | 거주지 | 이번 화의 변경 |
|---|---:|---|---|
| 1화 | 10세 | 서울 | 인물 최초 등록 |
| 2화 | 12세 | 서울 | 나이 10→12 (시간 경과 근거 필요) |
| 3화 | 12세 | 제주 | 거주지 서울→제주 |
| 4화 | 12세 | 부산 | 거주지 제주→부산 |
| 5화 집필 시 | 12세 | 부산 | 4화 종료 상태만 기본 제공 |

1화 조회 시 10세·서울, 3화 조회 시 12세·제주를 복원할 수 있다. 과거 회상 장면에서는 명시적 요청에 한해 과거 스냅샷과 사건 근거를 조회한다. **회차 번호와 이야기 속 날짜·시간은 별도로 관리**하여 회상, 시간 도약, 비선형 서술에 대응한다.

## 5. 원고 완료 후 엔티티 처리 흐름

1. **원고 완성**: 집필 AI가 회차 초안을 완성한다. 이때 공식 기억은 수정하지 않는다.
2. **엔티티 추출**: 엔티티 관리 AI가 인물·장소·조직·사물·사건·관계 등을 원문 근거와 함께 추출한다.
3. **동일성 연결**: 기존 DB를 조회하여 기존 엔티티와 연결하거나 신규 엔티티 후보로 분류한다. 애매한 경우 자동 병합하지 않는다.
4. **속성 변화 제안**: 직전 유효 상태와 비교해 신규·변경·유지·관계 종료 등을 구조화된 변경안으로 생성한다.
5. **연속성 검증**: 별도 AI가 시간·인과·소유권·세계 규칙·이전 확정 상태와의 충돌을 확인한다. 불일치는 오류, 설명 가능한 변화, 판단 보류로 구분한다.
6. **원고 수정 및 재추출**: 원고가 수정되면 변경 제안을 재생성하거나 영향을 받는 항목을 재검증한다.
7. **임시 상태 반영**: 10화 묶음 내 후속 회차 집필에는 검증된 임시 상태를 사용할 수 있다.
8. **작가 승인 후 확정**: 승인된 원고 버전과 변경 제안만 공식 변경 로그에 원자적으로 커밋한다.
9. **재작성 대응**: 앞선 회차가 수정되면 해당 회차 이후의 파생 상태와 검증 결과를 무효화하고 영향을 받는 회차를 재계산한다.

### 중요한 업무 경계

엔티티 관리 AI가 '주인공 나이가 12세에서 10세로 적혀 있다'고 추출하더라도 이를 즉시 확정하지 않는다. **추출은 관찰**, **검증은 판단**, **커밋은 승인된 변경의 저장**이다. 회상인지, 오기인지, 설정 변경인지 검증 후 결정한다.

## 6. AI 역할: 권장 논리적 역할 9종

| 역할 | 책임 | 실행 시점 |
|---|---|---|
| 총괄 디렉터 | 작업 흐름, 재시도, 승인 요청 조정 | 전 과정 |
| 아이디어 기획 AI | 작가와 소재·주제·세계관·인물 협의 | 기획 |
| 스토리 설계 AI | 200화 위계 구조와 10화 묶음, 회차 줄거리 | 집필 전·계획 수정 |
| 회차 연출 AI | 해당 화의 장면, 갈등, 감정선, 장면 전환 | 집필 직전 |
| 집필 AI | 회차 원고 작성, 필요한 현재 상태 및 예외적 과거 조회 | 집필 |
| 엔티티 관리 AI | 완성 원고에서 엔티티 추출·동일성 연결·변경 제안 | 집필 완료 후 |
| 연속성 검증 AI | 설정, 시간, 인과관계, 관계, 상태 충돌 검증 | 추출 후·수정 후 |
| 스토리 평가 AI | 몰입, 긴장감, 감정이입, 반복, 다음 화 기대감 | 원고 완성 후 |
| 문장 편집 AI | 문체, 가독성, 중복, 어색한 표현, 교정 | 검증·평가 후 |

**총괄 디렉터를 반드시 LLM 에이전트로 구현할 필요는 없다.** 초기에는 일반 프로그램의 상태 머신과 정책으로 구현하는 편이 비용·재현성·디버깅 측면에서 유리하다. 역할은 논리적 책임이며, 별도의 모델 인스턴스 수를 의미하지 않는다.

## 7. 초기 MVP의 5개 AI 역할 묶음

1. **기획 AI** = 아이디어 기획 + 스토리 설계
2. **집필 AI** = 회차 연출 + 본문 집필
3. **엔티티 관리 AI** = 추출 + 동일성 후보 + 변경 제안
4. **연속성 검증 AI** = 설정·시간·인과·관계 검증
5. **품질 편집 AI** = 스토리 평가 + 문장 편집

추가로 **워크플로 엔진(일반 프로그램)** 이 작업 순서, 데이터베이스 조회, 재시도, 임시 상태, 승인, 버전 관리, 커밋을 담당한다. 독자 관점 평가는 초기에는 품질 편집 AI의 별도 평가 프롬프트로 실행하고 필요할 때 독립 역할로 분리한다.

## 8. 집필 전·집필 중 정보 공급

- **집필 전**: 확정된 해당 화 줄거리를 분석하여 필요한 인물·장소·조직·사건 엔티티를 추린 후, 직전 화 종료 상태를 제공한다.
- **집필 중**: 줄거리에서 예상하지 못한 엔티티가 필요하거나 회상·과거 사건 확인이 필요할 때만 조회 도구를 호출한다.
- **집필 후**: 완성 원고 전체를 대상으로 추출·변경 제안·검증을 수행한다.
- **미래 계획**: 30화에 등장할 예정이라는 계획은 별도 플롯 데이터에만 보관한다. 5화의 공식 상태에는 미래를 추정하여 기록하지 않는다.

## 9. 권장 DB 테이블 및 도구 API

| 테이블 | 기능 |
|---|---|
| `entities` | 엔티티 정체성과 유형 |
| `entity_aliases` | 별칭·이름 후보 및 동일성 근거 |
| `entity_changes` | 승인된 속성 변경 로그 |
| `entity_snapshots` | 특정 회차 종료 상태 캐시 |
| `entity_relations` | 관계 및 유효 기간 |
| `events` | 독립 사건과 원인·결과 |
| `event_participants` | 사건에 참여한 엔티티 |
| `entity_mentions` | 원고 내 등장 위치와 인용 근거 |
| `change_proposals` | 승인 전 임시 변경 제안 |
| `manuscript_revisions` | 원고 버전과 승인 상태 |

권장 도구 인터페이스(예시):

- `get_entity_state(entity_id, episode_no, revision_scope)`
- `search_entities(name_or_context, episode_no)`
- `get_entity_history(entity_id, from_episode, to_episode)`
- `get_related_events(entity_id, time_range)`
- `propose_entity_changes(episode_no, manuscript_revision_id, proposals)`
- `validate_change_proposals(episode_no, proposal_set_id)`
- `commit_approved_episode(episode_no, manuscript_revision_id, proposal_set_id)`

쓰기 API는 서버 측 스키마 검증, 중복 요청 방지, 승인 권한, 버전 충돌 검사 및 트랜잭션을 적용한다. AI가 임의 SQL을 직접 실행하지 않도록 한다.

## 10. 구현 시 필수 검증 사례

1. **나이 변화**: 1화 10세 → 2화 12세. 시간 도약 근거가 있으면 정상 변화, 없으면 검증 보류.
2. **미언급 유지**: 5화에서 거주지가 언급되지 않아도 4화의 부산 거주 상태 유지.
3. **회상**: 20화에서 10세 시절 회고 시 1화 상태와 원문 근거 조회. 현재 나이를 10세로 덮어쓰지 않음.
4. **관계 변화**: 4화에 검 소유 → 8화에 분실. 인물·사물·관계 상태의 정합성 확인.
5. **동명이인**: 이름이 같은 두 인물을 자동 병합하지 않음.
6. **수정 전파**: 7화 수정 시 8~10화 임시 상태 및 연속성 검증을 재수행.
7. **승인 경계**: 작가 승인 전에는 공식 엔티티 상태가 변경되지 않음.
8. **원문 근거**: 추출한 모든 중요한 변경 제안이 원고 위치와 연결됨.

## 11. 남은 설계 결정

- 사건을 공통 `entities`에도 등록할지, `events` 전용 레코드로만 둘지
- 관계의 단방향·양방향 의미와 종료 규칙
- 상태 속성별 신뢰도 및 '불명' 표현 방식
- 몇 회마다 스냅샷을 저장할지(매회 저장 vs 주기적 캐시)
- 검증 오류의 심각도와 자동 수정 재시도 횟수
- 10화 묶음 승인 시 일부 화만 재승인하는 절차
- 독자 관점 평가 AI를 독립 실행할 시점

## 12. 결론

시스템의 중심은 **'엔티티 상태는 최신값만 기본 제공하되, 변화의 이유와 과거는 추적 가능하게 보존한다'**는 원칙이다. AI는 완성 원고에서 사실을 추출하고 검증하며, 프로그램은 승인된 변경만 안전하게 기록한다. 이를 기반으로 장편소설의 일관성을 유지하면서도 매회 AI에 전달하는 문맥과 처리 비용을 통제할 수 있다.
