## Phase 0. 방향 확정과 개발 기반

목적: 코드 작성 전 모든 "둘 중 하나"를 하나로 만든다.

- 제품 방향 확정: 자동 창작 플랫폼으로 간다면 구 데모 시나리오·제출 초안 폐기 선언
- 문서 위계 선언: 충돌 시 기획서 > Architecture > Memory 순 (또는 정하는 순서대로)
- 단일안 채택:
  - DB·API·변경연산은 Architecture안으로 통일, Memory안은 폐기
  - MVP 엔티티 유형은 인물·장소 2종부터
  - AI 역할은 MVP 5묶음(기획·집필·엔티티관리·검증·품질편집) + 프로그램 상태머신
  - 승인은 회차 단위, 10화 묶음은 진행률 라벨로만
  - 스냅샷은 매회 저장, 사건은 events 전용 테이블
  - 스택은 FastAPI + SQLite로 시작 (스키마만 PostgreSQL 이식 가능하게)
- 수치 결정: 회차 목표 분량, 자동 수정 최대 재시도(예: 3회), 회차당 비용·시간 상한
- 해커톤 상태 확인: 승인 여부, 크레딧 잔액·만료, 제출 폼 최신 항목
- 저장소 초기화: README 뼈대, .env.example, 라이선스, 키 노출 검사

완료 기준: 결정 기록 1건(위 항목 전부 값 채움), 빈 프로젝트가 깨끗한 환경에서 실행됨.

## Phase 1. 모델 연결 검증

목적: "된다고 가정한 것"을 실측으로 바꾸고 실증 범위를 확정한다.

- 모델 목록 조회, Muse Spark 실호출, 한국어 구조화 출력 파싱 확인
- 200화 개요 소규모 사전 실험: 예컨대 20화분만 생성해 비용·시간·품질 측정 후 전체/일부 결정
- 인용 대조 방식 프로토타입: 문자열 일치 vs 정규화(공백·조사) 매칭 중 선택
- 호출 1회당 토큰·비용·지연 기록 양식 확정

완료 기준: 실측표(모델 ID·지연·비용) 존재, 실증 범위 확정(200화 전체 vs 일부 vs N화),
인용 대조 방식 결정.

## Phase 2. 기억 데이터 기반

목적: LLM 없이도 회차별 상태가 정확히 재현되는 저장소를 만든다.

- 테이블 구현: entities, aliases, changes, snapshots, relations, events,
  mentions, proposals, revisions
- 핵심 동작: 회차별 상태 재구성, 임시/공식 분리, 승인 시 원자적 커밋(멱등),
  버전 충돌 검사
- 픽스처로 검증 (LLM 없이 프로그램 테스트):
  - 1화 10살→2화 12살, 회차별 조회 복원
  - 미언급 속성 유지, 명시적 변경만 반영
  - 회상 내용이 현재 상태를 덮어쓰지 않음
  - 미승인 변경이 다음 화 공식 기억에 유입되지 않음
  - 별명 vs 동명이인 자동 병합 금지

완료 기준: 위 케이스 전부 통과, 스냅샷 재구성 결과가 매번 동일.

## Phase 3. 기획·설계 파이프라인

목적: 키워드에서 승인된 서사 설계도까지.

- 키워드 입력 → 콘셉트 협의 대화 → 전체 구간 → 10화 묶음 → 회차별 개요 생성
- 회차 개요 필드: 번호·가제·목표·사건·인물변화·복선·전후 연결·제약
- 설계도 버전 관리 + 작가 승인 UI
- 설계 vs 실집필 불일치 시 처리 절차 정의
  (추적만 할지, 후속 계획 자동 수정 후 재승인할지)

완료 기준: 샘플 작품 1건의 설계도가 승인 상태로 저장됨.

## Phase 4. 집필 파이프라인

목적: 승인된 설계도와 상태로 원고 초안을 만든다.

- 집필 전: 해당 화 개요에서 필요 엔티티 선별 → 직전 승인 회차 종료 상태만 주입
- 집필 중: 예상 외 엔티티·과거 회상 조회 도구 호출 허용, 신규 창작은 임시로만
- 원고 버전 관리 (revision 저장, 수정 시 이전 버전 보존)

완료 기준: 설계도 기반 1~2화 초안이 버전과 함께 생성됨.

## Phase 5. 검증·기억 파이프라인

목적: 완성 원고에서 사실을 뽑아 근거와 함께 검증한다.

- 추출 → 동일성 연결 → 변경안 생성 → 연속성 검증 → 임시 반영
- 검증 판정 3분류: 오류 / 설명 가능한 변화 / 판단 보류
- 인용 대조를 통과한 근거만 충돌 증거로 제시,
  실패분은 "근거 미확인"으로 분리 표시
- 주입 테스트: 의도적 설정 충돌(예: 쿨다운 위반)을 넣고 탐지·근거 제시 확인

완료 기준: 주입 충돌 탐지 성공, 모든 변경안에 원고 위치 연결,
보류 건이 오류로 확정되지 않음.

## Phase 6. 품질·승인·커밋

목적: 작가 검토부터 다음 화 반영까지 1사이클 완주.

- 품질 편집(스토리 평가 + 문장 교정) → 품질 게이트 → 실패 시 DRAFT/EDIT 복귀
  (재시도 상한 적용)
- 상한 초과 시 미해결 이슈와 함께 작가에게 에스컬레이션 (무한 루프 금지)
- 작가 검토 화면: 진행률, 원고·요약·오류·수정내역·남은 이슈,
  회차 수정 요청, 전후 비교, 승인
- 승인 시 원고+기억 원자적 커밋 → 다음 화 집필에 반영 확인
- 앞 회차 수정 시 영향받는 후속 회차 무효화·재검증 범위 규칙 구현

완료 기준: 초기화 상태에서 설계승인→집필→검증→승인→커밋→다음화 반영을 연속 3회 성공.

## Phase 7. 평가와 기록

목적: 제출 자료에 쓸 "실측"을 만든다.

- 지표 측정: 주입 충돌 정밀도/재현율, 인용 정확도, 수정 후 재발률,
  워크플로 완주율, 회차별 비용·시간
- 프롬프트 조정용과 최종 확인용 케이스 분리, 표본 규모·한계 기록
- 가능하면 작가 1~2명 관찰 (수동 확인 vs 도구 사용 비교),
  불가면 본인 timed 비교로 대체
- 미측정 수치는 주장하지 않음, 미구현 기능 목록화

완료 기준: 평가 기록표 1건 (케이스별 정답·예측·근거·지연·비용).

## Phase 8. 제출물 완성

목적: 심사자가 재현할 수 있는 패키지로 묶는다.

- 배포 또는 깨끗한 환경 재현 절차 확정 (접속 경로·계정·초기화·복구 안내)
- README 완성: 문제·구현 범위·Meta 활용·실행·재현·평가·한계·라이선스
- 자작 샘플 원고·설정집·정답 케이스 동봉, 키·개인정보·비공개 원고 제거 확인
- 3분 영상: 문제→설계승인→자동집필→충돌탐지→근거·수정→승인·기억확정→평가결과
- 제출 폼 작성 (실측값만), 제출 후 완료 화면·시각·버전·링크 증빙 보관

완료 기준: 로그아웃 상태에서 저장소·영상 접근 확인, 제출 증빙 보관됨.

## 축소 순서 (일정 압박 시 자르는 순서)

1. 200화 전체 개요 → 일부 구간 개요로 축소
2. 품질 편집의 스토리 평가 분리 (교정만 유지)
3. 10화 묶음 개념 (회차 승인만 유지)
4. 이미지·구술 입력 (이미 범위 밖, 건드리지 않음)
5. 절대 자르지 않는 것: 추출→검증→승인→커밋 연결, 근거 대조, 재현 절차, 영상
