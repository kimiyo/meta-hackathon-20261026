# StorySpine 한국·미국 지원 구현 계획

## 1. 목표와 범위

StorySpine에 한국과 미국을 선택하는 기능을 추가한다. 미국을 선택하면 화면을 영어로 표시하고, 미국 시장을 대상으로 하는 영어 장르 프리셋과 영어 AI 프롬프트를 사용한다.

향후 영국·일본·중국·싱가포르·캐나다 등을 추가할 때 국가별 조건문을 반복하지 않도록 **화면 언어, 작품의 집필 언어, 대상 시장을 분리**한다.

이번 구현 범위:

- 한국어·영어 화면과 국가 선택
- 한국·미국 작품 설정
- 한국어·영어 AI 프롬프트
- 한국·미국 장르 프리셋
- 언어별 분량·제약·일관성 검증
- 기존 한국어 데이터와 API 호환
- 두 언어의 전체 창작 흐름 검증

결제, 해외 법률 대응, 해외 배포 인프라 등은 별도 범위로 둔다.

## 2. 핵심 설계

### 2.1 국가, 화면 언어, 집필 언어를 분리

사용자에게는 간단하게 국가를 선택하게 하되, 내부에서는 다음 설정을 별도로 저장한다.

| 설정 | 의미 | 한국 기본값 | 미국 기본값 |
|---|---|---|---|
| `market` | 작품의 대상 시장과 장르 프리셋 기준 | `KR` | `US` |
| `ui_locale` | 메뉴·안내·오류의 표시 언어 | `ko-KR` | `en-US` |
| `writing_locale` | 원고와 AI 창작 결과의 언어 | `ko-KR` | `en-US` |

동작 원칙:

1. 국가를 처음 선택하면 해당 국가의 기본 언어와 시장을 적용한다.
2. 화면 언어는 사용자 환경 설정으로 관리한다.
3. 집필 언어와 대상 시장은 작품별로 저장한다.
4. 화면 국가를 바꾸어도 기존 작품의 언어·시장·원고는 자동 변경하지 않는다.
5. 작품 생성 시 현재 국가를 기본값으로 제안하되, 저장된 값이 이후 AI 작업의 기준이 된다.

예를 들어 화면을 영어로 바꾸고 한국어 작품을 열면 메뉴는 영어로 표시하되, 해당 작품의 AI 생성 결과는 한국어로 유지한다.

### 2.2 초기 지원 범위

| 시장 | 화면 언어 | 기본 집필 언어 | 프리셋 |
|---|---|---|---|
| 한국 `KR` | `ko-KR` | `ko-KR` | 기존 한국 웹소설 프리셋 |
| 미국 `US` | `en-US` | `en-US` | 미국 시장용 영어 프리셋 |

화면에 영어·한국어 전환을 제공하되, 미국과 한국 이외의 국가를 선택지에 미리 노출하지 않는다. 추가 국가가 실제로 준비되었을 때 등록한다.

## 3. 국가·언어 설정 관리

### 3.1 지원 설정 레지스트리

국가와 언어의 지원 여부를 한곳에서 관리한다. 예시:

```python
MARKETS = {
    "KR": {
        "default_ui_locale": "ko-KR",
        "default_writing_locale": "ko-KR",
        "preset_catalog": "kr",
        "default_length_unit": "characters",
    },
    "US": {
        "default_ui_locale": "en-US",
        "default_writing_locale": "en-US",
        "preset_catalog": "us",
        "default_length_unit": "words",
    },
}
```

실제 구현에서는 등록 정보와 프리셋 데이터를 별도 파일로 관리해도 된다. 새로운 국가를 추가할 때 각 기능에 `if market == ...`을 반복하지 않는다.

서버는 지원하는 국가·언어와 각 기본값을 API로 제공하고, 프론트엔드 선택지는 그 응답을 사용한다.

```http
GET /api/v1/locales
```

응답 예시:

```json
{
  "markets": [
    {
      "code": "KR",
      "name_key": "market.KR",
      "default_ui_locale": "ko-KR",
      "default_writing_locale": "ko-KR"
    },
    {
      "code": "US",
      "name_key": "market.US",
      "default_ui_locale": "en-US",
      "default_writing_locale": "en-US"
    }
  ],
  "ui_locales": ["ko-KR", "en-US"]
}
```

`name_key`는 화면 번역 사전에서 국가명을 찾는 데 사용한다.

### 3.2 지원하지 않는 값 처리

- 등록되지 않은 국가·언어는 작품 생성 또는 변경 시 명확한 오류로 거부한다.
- 필수 프롬프트가 빠진 언어는 해당 기능을 실행하지 않고 오류를 기록한다.
- 미국 작품인데 한국어 프롬프트로 조용히 대체하는 동작은 허용하지 않는다.
- 화면 번역 누락은 개발·테스트에서 탐지하고, 운영 화면에서는 정의된 대체 언어와 오류 기록 정책을 적용한다.

## 4. 데이터베이스와 API

### 4.1 작품별 설정 저장

현재 `server/app/db.py`의 `works` 테이블에는 시장이나 집필 언어가 없다. 다음 필드를 추가한다.

```text
works.market           TEXT NOT NULL DEFAULT 'KR'
works.writing_locale   TEXT NOT NULL DEFAULT 'ko-KR'
```

기존 작품에는 `KR`, `ko-KR`을 적용한다. 기존 작품의 원고, 설정, 집필 이력과 사용자 지정 문체는 변경하지 않는다.

### 4.2 화면 설정 저장

초기 버전에서는 로그인 전에도 동작하도록 브라우저의 `localStorage`에 다음 값을 저장한다.

```text
preferred_market
ui_locale
```

이 설정은 브라우저별이다. 다른 기기와 화면 설정을 동기화해야 한다면 이후 작성자 계정 설정에 저장하는 기능을 추가한다. 작품 설정은 서버에 저장하므로 다른 기기에서도 유지된다.

### 4.3 작품 생성 API 확장

현재 `server/app/routes/works.py`의 작품 생성 API를 확장한다.

```json
{
  "title": "The Last Bookshop",
  "market": "US",
  "writing_locale": "en-US"
}
```

응답에도 저장된 값을 포함한다. 이전 클라이언트가 새 필드를 보내지 않으면 기존 동작을 유지하도록 한국·한국어를 적용한다.

### 4.4 기존 작품 설정 변경 정책

집필 중 국가·언어를 바꾸면 기존 설정과 새 결과가 섞일 수 있으므로 초기 버전은 다음처럼 제한한다.

- 작품 생성 직후 AI 생성 콘텐츠가 없는 경우: 시장·집필 언어 변경 허용
- AI 생성 콘텐츠 또는 원고가 생긴 이후: 시장·집필 언어 변경 제한
- 화면 언어는 언제든 변경 가능
- 기존 원고를 다른 언어로 번역하거나 다른 시장용으로 전환하는 기능은 별도 작업으로 다룸

판정 기준인 ‘AI 생성 콘텐츠 또는 원고가 존재하는가’는 작품에 연결된 대화, 설계, 원고 데이터를 기준으로 서버에서 검사한다. 프론트엔드에서만 제한하지 않는다.

### 4.5 마이그레이션

`server/app/db.py`의 기존 마이그레이션 방식과 통합하되 다음을 보장한다.

- 새 DB와 기존 DB 모두 정상 동작
- 마이그레이션 재실행 시 중복 변경 없음
- 기존 작품은 한국·한국어로 설정
- 프리셋 키와 사용자 지정 문체 유지
- 마이그레이션 전후 작품 수·원고·설정 데이터 비교
- 실행 전 DB 백업과 복구 절차 마련
- `llm_calls` 호출 추적 컬럼 추가 (market, writing_locale, 프롬프트 기능명·버전, 프리셋 ID·버전)

### 4.6 발간 플랫폼 기본값

`works.platform`과 `publish_editions.platform`의 기본값이 현재 `'문피아'`로 고정되어 있다.
시장별 기본값을 다음과 같이 적용한다.

- 기존 작품: 저장된 값 유지 (마이그레이션에서 변경하지 않음)
- 신규 한국 작품: 기존과 같이 `'문피아'` 기본
- 신규 미국 작품: 미국 시장용 기본값을 출시 전 확정. 확정 전까지는 빈 문자열을 허용하고
  발간 화면에서 명시적 선택을 요구한다. 한국 플랫폼명을 미국 작품에 자동 적용하지 않는다.

## 5. 프론트엔드 i18n

현재 프론트엔드는 빌드 과정 없는 정적 HTML·JavaScript이므로, 현재 구조에 맞는 경량 i18n 계층을 추가한다. 특정 라이브러리 도입 여부는 복수형 처리와 유지보수성을 확인한 후 결정한다.

### 5.1 번역 파일 구성

예시:

```text
frontend/
  locales/
    ko-KR.json
    en-US.json
  js/
    i18n.js
```

```json
{
  "nav.ideas": "Ideas",
  "nav.design": "Story Design",
  "nav.writing": "Writing",
  "work.create": "Create a Novel",
  "work.count": "{count} novels"
}
```

번역 키는 화면상의 문구 자체가 아니라 기능을 나타내는 안정적인 이름으로 정한다.

### 5.2 적용 대상

`frontend/index.html`과 `frontend/js/` 전체에서 다음을 번역 대상으로 추출한다.

- 메뉴, 탭, 버튼, 폼 라벨
- 안내문, 빈 상태, 로딩 및 오류 메시지
- `placeholder`, `title`, 접근성 라벨
- JavaScript에서 동적으로 생성하는 HTML과 문자열
- 확인창, 입력창, 저장 실패 메시지
- 숫자·날짜·시간 표시
- `frontend/manual.html`의 사용 설명
- 페이지 제목 및 언어 관련 메타데이터

국가 변경 시 현재 화면의 문구를 다시 그리거나, 필요한 경우 페이지를 안전하게 새로 고친다. **작성 중인 입력값은 보존**하도록 처리한다.

### 5.3 날짜·숫자

`frontend/js/manuscript.js`의 `ko-KR`, `Asia/Seoul` 고정을 제거하고 `Intl`을 사용한다.

- 언어별 날짜·숫자 형식 적용
- 시간대는 기본적으로 사용자 브라우저 설정 사용
- 서버 저장 시간은 기존 UTC 유지

### 5.4 서버 오류 표시

현재 `frontend/js/api.js`는 서버 오류 본문을 그대로 보여주는 경로가 있다. 단계적으로 다음 형태를 적용한다.

```json
{
  "detail": {
    "code": "WORK_TITLE_REQUIRED",
    "params": {}
  }
}
```

화면은 `code`를 현재 화면 언어의 번역 키로 변환한다. 기존 API 소비자를 고려해 이전 오류 형식도 한동안 처리한다. 원고 충돌처럼 현재 사용 중인 `code`, `latestRevision` 등 추가 필드는 유지한다.

## 6. AI 프롬프트 관리

### 6.1 프롬프트 선택 기준

AI 호출 시 작품의 `writing_locale`과 `market`을 기준으로 프롬프트 묶음을 선택한다.

```text
작품 설정
  ├─ writing_locale: en-US
  └─ market: US
          ↓
공통 기능 규칙 + 영어 지시문 + 미국 시장 지침 + 선택된 장르 문체
```

공통 규칙을 반드시 코드에서 문자열로 조립해야 하는 것은 아니다. 구현과 검증이 쉬운 형태로 관리하되, 언어별 문장과 시장별 창작 지침의 책임을 분리한다.

예시 구조:

```text
server/app/prompts/
  ko-KR/
    planning.txt
    drafting.txt
    verify.txt
    ...
  en-US/
    planning.txt
    drafting.txt
    verify.txt
    ...
  markets/
    KR/
    US/
```

영국을 위한 문구가 나중에 필요해질 수 있으므로 공통 영어와 지역별 차이를 분리할 수 있도록 프롬프트 로더의 선택 규칙도 마련한다. 단, 집필에 필수인 언어 자료가 없을 때 다른 언어로 자동 대체하지 않는다.

### 6.2 전체 AI 호출 경로 적용

현재 프롬프트는 파일과 Python 코드 양쪽에 흩어져 있다. 다음 기능을 모두 대상으로 목록을 작성하고, 각 호출이 작품 설정을 전달하도록 변경한다.

| 기능 | 주요 현재 위치 |
|---|---|
| 아이디어 대화·추출·인계 | `routes/ideas.py` |
| 작품 설계·개요 | `planning.py` |
| 설계 대화·노드 확장 | `routes/design_threads.py`, `routes/nodes.py` |
| 집필·재집필 | `drafting.py` |
| 인물·설정 추출 | `extraction.py` |
| 검증·품질 평가 | `verification.py`, `quality.py` |
| 일관성 분석·대화 | `consistency.py` |
| 발간 소개글 생성 | `publishing.py` (`prompts/blurb.txt`) |
| JSON 복구 재요청 | `meta_client.py` |
| 모델 연결 검증 | `routes/ops.py` |

모델 연결 검증처럼 작품에 속하지 않는 호출은 작품 언어와 무관한 별도의 내부 진단 정책을 적용한다.

### 6.3 동적 지시문과 출력 언어

프롬프트 파일뿐 아니라 Python 코드에서 생성하는 지시문도 언어별로 관리한다. 예를 들어 `planning.py`의 `키워드`, `총 회차`, `생성하라` 등의 지시가 대상이다.

각 AI 기능에는 출력 언어를 명시한다.

- 원고, 아이디어 답변, 줄거리, 검토 설명: 작품 집필 언어
- JSON 키, 내부 상태값, 식별자: 언어에 관계없이 기존 형식 유지
- 사용자가 제공한 원문, 이름, 인용: 임의로 번역하지 않고 보존
- 한국어 작품에서 영어 화면을 사용하는 경우에도 AI 창작 결과는 한국어 유지

### 6.4 버전과 추적성

AI 호출마다 다음 정보를 로그에 기록할 수 있도록 확장한다.

```text
작품 ID
market
writing_locale
프롬프트 기능명
프롬프트 버전
프리셋 ID 및 버전
```

호출 중 작품 설정이 바뀌어도 한 번 시작된 작업에서는 동일한 설정을 사용하도록 작업 시작 시 설정을 확정한다. 저장된 원고와 과거 로그를 나중에 재해석하지 않는다.

## 7. 장르·문체 프리셋

### 7.1 데이터 구조

현재 `server/app/style_presets.py`의 전역 프리셋을 시장별 카탈로그로 확장한다.

```text
id
market
version
label
description
pov
diction
feedback
```

화면용 `label`, `description`과 AI용 `pov`, `diction`, `feedback`의 역할을 구분한다.

### 7.2 초기 프리셋

**한국**

- 퓨전판타지·헌터물
- 로맨스·로맨스판타지
- 미스터리·스릴러
- 정통 문학풍

기존 프리셋의 의미와 저장된 값은 유지한다.

**미국**

- Fantasy
- Romance
- Mystery / Thriller
- Science Fiction
- Literary Fiction

미국 프리셋은 영어로 작성하고, 각 장르의 시점·문장·전개 방향을 제공하되 작가가 사용자 지정 문체로 수정할 수 있게 한다. 미국 장르 관행을 일률적으로 고정하지 않도록 프리셋 문구는 실제 영어 집필 결과를 보고 조정한다.

### 7.3 기존 프리셋과 사용자 문체

현재 프리셋을 적용하면 문체 값이 작품에 스냅샷으로 저장된다. 이 동작을 유지한다.

- 기존 `fusion-fantasy`, `romance` 등의 한국 프리셋 키 유지
- 미국 프리셋은 충돌하지 않는 안정적인 ID 사용
- 프리셋 내용이 이후 바뀌어도 기존 작품의 스냅샷은 자동 변경하지 않음
- 사용자가 저장한 문체는 임의 번역하거나 덮어쓰지 않음
- 선택된 작품의 시장에 맞는 기본 프리셋 목록 제공

## 8. 분량과 검증

### 8.1 문자 수와 단어 수

현재 `server/app/drafting.py`는 Python의 `len(text)`로 분량을 검사한다. 이를 단위가 명시된 정책으로 확장한다.

```text
length_min
length_max
length_unit: characters | words
```

- 기존 한국 작품: 현재와 같은 문자 수 기준 유지
- 신규 한국 작품: 문자 수 기본
- 신규 미국 작품: 단어 수 기본
- 화면에 목표와 실제 분량의 단위를 명확하게 표시
- 영어 단어 수 계산 규칙을 하나로 정하고 화면·서버에서 일치시킴
- 발간 AI 소개글 상한(현재 한국어 500자 기준)은 영어용 단어 수 기준을 별도로 정함

영어 기본 목표 분량은 기존 한국어 문자 수를 기계적으로 환산하지 않고, 실제 생성 결과와 제품에서 의도하는 회차 길이를 기준으로 정한다.

현재 토큰 예산 산정은 한국어 실측에 기반한 비율을 사용하므로, 영어의 단어 수 및 출력 토큰 사용량을 실측해 별도 기준을 정한다. 모델이 목표 분량을 지원하지 못할 경우를 대비해 상한과 오류 처리도 확인한다.

### 8.2 필수·금지 제약

현재는 `필수:`, `금지:` 문자열을 직접 인식한다. 사용자 표시 언어와 내부 검증을 분리하기 위해 구조화된 제약을 추가한다.

```json
{
  "type": "required_phrase",
  "value": "the silver key"
}
```

```json
{
  "type": "forbidden_phrase",
  "value": "it was all a dream"
}
```

기존 한국어 문자열은 계속 읽을 수 있도록 호환 경로를 유지한다. 새 화면에서 만드는 제약부터 구조화 형식을 사용하고, 데이터 변환 여부는 기존 저장 형식과 이력 보존을 확인한 후 결정한다.

### 8.3 일관성 검사

`server/app/checks.py`에는 한국어 단서와 한국어 어간을 가정한 규칙이 있다.

- 한국어 전용 규칙이 영어 작품에 잘못 적용되지 않도록 분리
- 영어 데이터에서 횟수 제한·속성 관계가 제대로 검출되는지 점검
- 가능한 부분은 언어별 문자열 추측보다 구조화된 속성과 식별자를 사용
- 규칙 기반 검사와 AI 의미 검사 각각의 한계를 표시
- 검사 결과의 제목·설명도 화면에서 영어로 이해할 수 있도록 처리

영어 지원을 위해 기존 한국어 검사의 동작이 퇴행하지 않도록 별도 회귀 테스트를 둔다.

## 9. 백엔드 메시지와 사용자 콘텐츠

| 데이터 | 처리 방식 |
|---|---|
| 시스템 오류·상태 메시지 | 오류 코드와 번역 매개변수로 전달 |
| AI가 생성한 줄거리·검토 의견 | 작품의 집필 언어로 생성·저장 |
| 사용자가 작성한 원고·이름·설정 | 원문 그대로 저장 |
| 내부 JSON 키·상태 코드 | 공통 형식 유지 |
| 과거에 저장된 한국어 AI 결과 | 자동 번역하지 않고 유지 |

이 구분이 있어야 영어 화면에서 기존 한국 작품을 열었을 때, 시스템 UI는 영어로 표시하면서 작품의 실제 내용은 보존할 수 있다.

서버 코드에 직접 적힌 한국어 문구(예: `routes/ideas.py`의 생략 표시 `…(이하 N자 생략)`,
`publishing.py`의 `AI가 빈 소개글을 반환했습니다`)도 번역 전에 전수 목록을 작성한다.
시스템·상태 성격의 문구는 오류 코드로 전환하고, 작품 내용과 함께 저장·표시되는 문구는
작품의 집필 언어에 맞는 문구로 생성한다.

## 10. 구현 단계와 완료 조건

### 단계 1. 설정 기반과 데이터 호환

**작업**

- 지원 국가·언어 레지스트리 추가
- 작품의 `market`, `writing_locale` 저장
- 화면 설정 저장
- 기존 작품 마이그레이션
- 작품 생성·조회 API 확장
- 생성 이후 작품 언어 변경 제한 적용
- 시장별 발간 플랫폼 기본값 적용

**완료 조건**

- 기존 작품이 `KR` / `ko-KR`로 열림
- 새 미국 작품이 `US` / `en-US`로 저장됨
- 새 미국 작품에 한국 플랫폼 기본값이 들어가지 않음 (기존 작품의 값은 유지)
- 화면 국가 변경이 기존 작품을 바꾸지 않음
- 기존 API 요청과 데이터가 정상 동작

### 단계 2. 화면 i18n

화면 범위가 넓으므로(`index.html` + JS 16개 모듈 + 사용 설명서) 화면 단위로 나누어 적용한다.

**작업 2a. 기반**

- 번역 파일과 i18n 계층 추가
- 국가 선택 화면 추가
- 공통 내비게이션·다이얼로그·오류 표시의 번역 적용

**작업 2b. 화면별 적용 (순서대로)**

1. 아이디어 → 2. 설계 → 3. 집필 → 4. 검토 → 5. 발간
2. 각 화면의 메뉴·버튼·안내·빈 상태·동적 문구를 번역하고, 해당 화면만 영어로 전환해 검수한다.

**작업 2c. 마무리**

- `manual.html` 사용 설명서 번역
- 날짜·숫자 `Intl` 전환과 서버 오류 코드 표시 처리

**완료 조건**

- 미국 선택 시 주요 화면, 커스텀 다이얼로그, 오류 및 설명서가 영어로 표시됨
- 한국 선택 시 기존 한국어 사용 흐름이 유지됨
- 입력 중 전환해도 작성 중인 내용이 유실되지 않음

참고: 네이티브 `confirm()`·`prompt()`의 버튼(확인/취소)은 브라우저 로케일을 따르므로
앱 번역 대상이 아니다. 영어 표시가 필요한 확인 흐름은 커스텀 다이얼로그로 교체한 뒤
완료 조건을 판정한다.

### 단계 3. 프롬프트와 프리셋

**작업**

- 전체 AI 호출 목록(발간 소개글 포함)을 기준으로 프롬프트 로더 적용
- 시스템·동적·복구 프롬프트 영어화
- 발간 소개글 프롬프트(`blurb.txt`) 영어화 및 단어 수 상한 적용
- 미국 장르 프리셋 추가
- 프롬프트 및 프리셋 버전 기록

**완료 조건**

- 미국 작품의 모든 창작 관련 AI 호출에 영어 지시문이 사용됨
- 한국 작품의 AI 호출은 기존 한국어 흐름을 유지함
- 미국 작품에서 미국 프리셋을 선택할 수 있음
- 필수 영어 프롬프트가 누락되면 한국어로 조용히 대체하지 않음

### 단계 4. 언어별 집필·검증

**작업**

- 문자 수·단어 수 정책 추가
- 필수·금지 제약 구조화 및 기존 데이터 호환
- 한국어 전용 일관성 검사 분리
- 서버 메시지 국제화

**완료 조건**

- 한국어 작품은 기존 문자 수 기준으로 검증됨
- 영어 작품은 표시된 단어 수 기준으로 검증됨
- 두 언어에서 필수·금지 문구와 주요 일관성 검사가 동작함

### 단계 5. 통합 평가와 출시 판단

**작업**

- 한국어·영어 각각 전체 창작 흐름 실행
- 실제 모델로 영어 결과 품질과 토큰 사용량 측정
- 미국 프리셋과 문구 검토
- 마이그레이션 및 복구 리허설

**완료 조건**

- 두 시장에서 아이디어 → 설계 → 집필 → 검토 → 발간 흐름 완료
- 기존 한국 작품을 열고 이어서 작업할 수 있음
- 영어 UI와 영어 생성 결과에 한국어 시스템 문구가 섞이지 않음
- 실제 모델 사용 시 목표 분량, JSON 형식, 검증 품질이 사전에 정한 기준을 충족함

## 12. 향후 국가 추가 방식

예를 들어 영국을 추가한다면 다음 자료를 준비한다.

1. `GB` 시장 등록과 기본 화면·집필 언어 지정
2. 영국 영어 화면 문구와 필요한 지역별 표현 추가
3. 영국 시장용 장르 프리셋 또는 기존 영어 프리셋의 재사용 범위 결정
4. 영국 영어 프롬프트와 공통 영어 프롬프트의 재사용 범위 결정
5. 분량·검증 규칙과 전체 흐름 테스트 추가

일본·중국처럼 언어가 다른 국가는 해당 언어의 화면 번역과 필수 프롬프트를 추가해야 한다. 국가 설정만 등록하면 자동으로 지원되는 구조가 아니라, 필요한 언어 자료와 검증이 준비된 국가만 활성화하는 구조다.

이 문서는 현재 코드 구조를 기준으로 작성한 설계안이며, 아직 코드 변경이나 실제 모델 성능 검증은 수행하지 않았다.
